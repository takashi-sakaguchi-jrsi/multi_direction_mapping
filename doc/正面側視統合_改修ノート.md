# 正面 / 側視統合 改修ノート

日付: 2026-10-01  
対象: 製品エントリ `src/main_twopass.py`（EXE 名 `main_twopass.exe`）  
関連: 側視の幾何・接合の採用事項は `doc/2方向動画合成カラーマップ生成_実装ノート.md`

製品版を **正面（オリジナル 2 パス）** と **側視（2/3 方向合成）** の 2 経路に分け、同一 EXE / 同一 4 層設定で切り替える。2026-10-01 時点で両経路の通し動作を確認した。

本ノートは統合の契約と、経路を混ぜないための制約を残す。次段階（正面のマッチングずれ）は §8。

---

## 1. 位置づけ

| 経路 | `pipeline` | 本体 | 入力 |
| --- | --- | --- | --- |
| 正面 | `front` | `ColorMapPipelineTwoPass` | 動画 1 本 |
| 側視 | `sideview`（既定） | `run_two_direction_validation` | `{name}_U` / `_R`（`_L` は任意） |

- 推定器・展開器・進捗 JSON・Excel 列は **経路ごとに別物のまま**。ColorMapGenerator や正面 Phase1/2 を側視に流用しない。
- JSON の `sideview` は `two_direction` の別名（`Config.sideview` が同一オブジェクト）。
- 検証用 CLI `src/main_two_direction_validation.py` は残す。製品から側視へ入るときは `main_twopass.py --pipeline sideview`。

---

## 2. CLI

4 層マージは従来どおり（dataclass 初期値 < `data/config/default_config.json` < `--config` < CLI）。`--pipeline` は Layer 4。

```bash
# 正面（ファイル指定）
python src/main_twopass.py --pipeline front --input data/input/videos/phi250_frontview.mp4 --start 1 --end 500

# 正面（フォルダ + 名前。{name}.mp4 → .avi → .mov → .mkv の先頭ヒット）
python src/main_twopass.py --pipeline front --input-dir data/input/videos --name phi250_frontview

# 側視（{name}_U/_R/_L。L が無ければ 2 方向。拡張子は同上）
python src/main_twopass.py --pipeline sideview --input-dir data/input/videos --name phi250_baseline_calib --config data/config/two_direction_config.json
```

| オプション | 正面 | 側視 |
| --- | --- | --- |
| `--input` | 動画ファイル 1 本 | 不可 |
| `--input-dir` + `--name` | `{name}.{ext}` | `{name}_U/_R/_L.{ext}` |
| `--start` / `--end` | 1 始まり、含む | 内部は `[start-1, end)` |
| `--z-source` | `ocr` / `known` | 同上（仮想検証は `known`） |

`--input` と `--input-dir/--name` は同時指定できない。`--input-dir` と `--name` は必ずセット。`--run-a` だけを付けた場合でも、省略した B/C を消さない（Layer 2 のパスが残る）。名前指定はプレフィックス一致で、先に当たった拡張子を使う。

`python src/main_twopass.py` でも `import src.*` が通るよう、リポジトリルートを `sys.path` 先頭へ入れる。

## 3. 設定

### 3.1 トップレベル

`data/config/default_config.json`:

- `pipeline`: 既定 `sideview`
- `z_source` / `known_z_metadata_path` / `save_ocr_metadata`
- `front`: 正面経路だけ上書きする衝突項目（VP 制約、yaw/pitch 上限 15°）。`apply_front_profile()` が `--pipeline front` のときだけ適用し、側視の既定は触らない

側視の仮想検証 overlay は `data/config/two_direction_config.json`（`z_source=known`、校正レンズで生成した `phi250_baseline_calib_{U,R,L}.mp4`）。

### 3.2 距離

- 実正面: `z_source=ocr`（Tesseract）。ROI は `camera.ocr_roi_ratio`（左上、距離表示）
- 仮想側視: `z_source=known`。metadata の z が処理区間 `[start, end)` を包含しないとエラー
- `save_ocr_metadata=true` のとき、OCR（または既知 z）系列を出力隣へ JSON 保存
- 仮想生成動画に距離 overlay は焼かない。`z_source=ocr` では読めない

### 3.3 OCR エンジンパス

WSL 通し確認では `ocr.tesseract_cmd` を `/usr/bin/tesseract` にした。`/user/bin/tesseract` は存在せず、例外が debug に落ちて成功 0 件になる。Windows 製品では従来どおり `%USERPROFILE%\AppData\Local\Programs\Tesseract-OCR\tesseract.exe` 等に差し替える。

### 3.4 出力

- 正面: `output.colormap_path` / `temporary_colormap_path` / 既存 Excel・`progress/progress.json`（旧 4 ステップ）
- 側視: `two_direction.output_dir` 配下の `mode_A/` など。製品出力へコピーしたあと、`colormap.delete_temporary_images=true` なら部分図・一時 PNG を消す（Excel と progress は残す）
- 進捗 JSON のステップ名・重み・Excel 列は経路で別。混ぜない

## 4. 入口分岐

`main()`:

1. `load_config` → `apply_product_cli`（pipeline / 入力 / start-end / z_source）
2. `effective_pipeline`
3. `front`: FrontConfig 適用 → 既知 z なら包含チェック → `ColorMapPipelineTwoPass.run()`
4. `sideview`: 作業ディレクトリ → 3 方向用 ProgressReporter → `run_two_direction_validation`

WSL など GUI 無し OpenCV では `cv2.destroyAllWindows` が未実装のため、`DebugVisualizer.close()` / `show_frame()` は `cv2.error` を握りつぶす。

## 8. 次段階（正面の移動量推定と展開精度）

正面は従来から円筒マッチングのずれが目立つ。側視 Mode A で効いている次の二つを、正面へ移植する検討に入る。

1. **パラメータ制限**  
   側視は x/y=0、yaw（光軸まわり捩れ）固定、推定は主に dz と dpitch。center prior と hard bounds で基準姿勢から大きく外さない。正面の 6DoF 近い探索は、観測できない自由度がマッチング誤差に載り、展開がずれる。

2. **定点振動仮定による座標補正**  
   仮想側視の姿勢は基準まわりの振動であり、積算ドリフトしない（`PoseJitterConfig`）。実機も管路内では大振幅の歩きより、基準姿勢のまわりの揺れが主だとみなす。推定座標（特に yaw/pitch、必要なら x/y）をその仮定で引き戻し、展開図の z/θ ずれを抑える。

正面経路の ColorMapGenerator / Phase1 VP・OCR は維持したまま、移動量推定の拘束と補正だけを足す。側視の接合ワープや 3 方向合成ロジックは正面に持ち込まない。
