## 1. 目的と非目的

### 1.1 目的

- 魚眼 3 方向（U/R/L、光軸 120°）を、ピンホール 8 方向（光軸 45°）へ置き換える
- 1 フレームのマッチ範囲と展開範囲を、正面のドーナツ半径比に相当する **画像縦方向の高さ割合** で独立に指定する
- 横方向はピンホールでフレーム全域に映像があるため **全幅を使う**。担当角の切り出しは異方向接合に任せる
- フレーム間マッチは **dz のみ**（Δpitch を積まない。消失点は無いので載せ替えもしない）
- 展開後の同一 Run 帯重なりで **絶対 (z, pitch) を直して取り直す**
- Phase2 末尾 deroll は側視に入れない。周方向の低周波は既存の接合ワープと pitch トレンドに残す

### 1.2 非目的

- 正面経路の改修、EXE 名の変更、経路の統合
- 正面 `front_strip_overlap.py` / `ColorMapGenerator._measure_and_maybe_correct_strip` の流用
- Kannala 校正 JSON をピンホール側視へ載せる実験の再開
- 帯幅を `max_dz × alpha` や仮の 40 mm に固定すること（40 mm は画角の目安議論であり、実装単位ではない）

### 1.3 経路を混ぜない制約（現行ノートと同じ）

- 推定器・展開器・進捗 JSON・Excel 列は経路ごとに別物
- `apply_front_profile()` は `--pipeline front` のときだけ
- `data/config/default_config.json` の現地実験値はコミットしない
- Δθ の DC を droll に載せない（側視でもマッチの自由変数に roll を増やさない）

## 2. 前提幾何（8 × 60° ピンホール）

管内中心、壁面正対。縦方向が管軸 Z、横方向が周方向 η。

| 量 | 値 |
| --- | --- |
| 画角 | 60°（ピンホール、`r = f tan θ`） |
| 台数 | 8 |
| 光軸間隔 | 45° |
| 隣接重なり | 各側 15°（FOV 60° − 間隔 45°） |
| 担当帯 | 重なり中央で分割 → 各 45° |
| カット線（カメラカー） | 22.5° + 45°·k（k = 0..7） |

カメラカー roll（真上が 0°、増やすと右）:

`0, 45, 90, 135, 180, 225, 270, 315`

隣接カメラ i と i+1 の重なりは `[45i+15, 45i+30]`°、カットはその中点 `45i+22.5`°。

φ250（半径 125 mm）で、光軸から進行方向へ高さ割合 `h`（半画角 30° に対する比、主点基準）を取ったときの壁面 Z は

\[
\Delta Z = R \tan\bigl(h \cdot 30^\circ\bigr)
\]

例: h=0.6 → 約 41 mm、h=1.0（半面）→ 約 72 mm。実装は mm をハードコードせず、縦割合と fy / 主点から毎回換算する。

### 2.1 ファイル名と run_id

製品入力は `{name}_{ccc}.{ext}`（`ccc` はカメラカー roll を 3 桁。`000` … `315`）。

互換: 既存の `{name}_U` は `000`（カメラカー 0°）の別名として読む。8 方向本番は `_000` 形式を正とする。

`{name}_R` / `{name}_L` は旧 3 方向の 120° / −120°（240°）であり、**8 方向の 45° 格子の隣カメラではない**。同名の R/L がフォルダにあっても、ピンホール 8 方向経路では自動で接合相手にしない。0° 単体テストは U（または `_000`）だけを run に載せる。

拡張子探索は現行どおり `.mp4 → .avi → .mov → .mkv` の先頭ヒット。欠ける方向はスキップし、存在する **45° 隣接** ペアだけ接合する。8 本揃わなくても解析は進めるが、欠ける接合は変位 0。現行コードは U+R 必須なので、工程 1 で 1 本（0° のみ）を許可する。

### 2.2 プログラム Euler

現行 `_CAPTURE_TO_PROGRAM_RPY_DEG` は (90°, 0/120/−120°) の 3 点表である。8 方向では廃止し、次の拘束からカメラごとにプログラム (roll, yaw, pitch) を出す。

1. 光軸が、カメラカー roll の壁（半径 R の XY 円周）を向く
2. カメラ上方向が管軸と直交し、画像 y 増加が +Z（進行）になる
3. U（0°）で現行 `(-90, 90, 90)` に一致することを回帰テストする

0° と 180° は pitch≈90° 特異点が残る。Mode A の残差座標（フレーム XY か円筒 3D か）は run_id 文字ではなく、**光軸が ±Y 近傍か**で切り替える。dz_only 採用後はマッチの自由角は無いが、逆投影と残差の座標系はこの分岐を残す。

### 2.3 レンズモデル

- `camera.camera_model = pinhole`。等距離魚眼（`r = fθ`）で 60° を近似しない
- 歪み係数は使わない（Kannala 順歪み・`distort_ideal_pixels` は側視ピンホール経路で恒等）
- 仮想動画の生成と解析は同じ f, cx, cy、k=0
- 本番魚眼校正 JSON（`fisheye_recalibrated_*.json`）は側視ピンホールに載せない。metadata にパスがあっても無視する

魚眼 3 方向の仮想検証は本改修の主経路から外す。必要な回帰はピンホール 8 方向（または本数を減らしたピンホール）で取り直す。

### 2.4 実写テスト入力（0° のみ）

今回対象のピンホール側視カメラで、カメラカー 0° を撮った実写:

| ファイル | 方向 | 用途 |
| --- | --- | --- |
| `data/input/videos/test01_hp250_U.mp4` | 0° | 方向別処理の単体通し（マッチ、縦割合展開、dz_only、帯重なり、OCR） |
| `data/input/videos/test02_hp250_U.mp4` | 0° | 同上の別走行 |

実測: 1920×1080、約 29.97 fps。`test01` 6451 フレーム、`test02` 4395 フレーム。

同フォルダの `test01_hp250_R.mp4` / `_L.mp4` および `test02` の R/L は旧 120° / −120° 配置なので、8 方向化の接合テストには使わない。異方向接合・n 周期化（工程 6）は仮想 8 方向動画、または後から揃う 45° 間隔の実写を待つ。

## 3. 正面改善 → 側視の対応

正面の実装を import しない。側視側に同型の設定キーと処理を置く。

| 正面 | 側視への適用 | 内容 |
| --- | --- | --- |
| ドーナツ `cylindrical.inner/outer_radius_ratio`（マッチ）と `colormap.inner/outer_radius_ratio`（展開） | **採用（縦割合に置換）** | マッチ用・展開用を独立の縦方向高さ割合にする。原点は画像上端ではなく主点 `cy` |
| ドーナツ外周の鮮明画素優先 | **不採用** | ピンホールはフレーム全域が使える。横は全幅 |
| `physical_attitude_source=dz_only` | **採用（VP 無し）** | マッチの積む量は dz のみ。Δpitch は 0。消失点載せ替えはしない |
| 帯重なり測定＋絶対 (z, roll) 取り直し | **採用（(z, pitch)）** | `BestViewAccumulator` 上に側視用を新設。`ColorMapGenerator` は使わない |
| leftover `drow→roll, dcol→z` | **置換** | leftover `dη→プログラム pitch`（周方向）、`dZ→z`。符号は実測で一度固定（正面と同じく「帯が先行していれば引く」） |
| Phase2 末尾 deroll | **不採用** | 異方向接合と pitch トレンドが周方向を吸収する |
| residual paste / overlap paste align | **不採用（既定）** | 正面でも帯重なりオン時は切る。側視は測定＋取り直しだけ |
| `reject_z_behind_camera` / prefer_peripheral | **不採用** | 正面ドーナツ用。側視の展開は進行方向の縦帯 |
| VP 制約・初期姿勢・θ を VP へ戻す | **不採用** | 側視に消失点は無い |
| OCR 比で異常に小さい dz → 失敗経路 | **採用** | `FrameAnalyzer` に入れる。統計は「Z方向矛盾」 |
| STATIC_FRAME | **入れない** | 正面と同じく Don't care。二重フレームは失敗／通常推定のどちらでもよい |
| 失敗時に prev を進め、履歴中央値 dz で z を進めて塗らない | **採用** | 現行側視 FAILED は pose も prev も凍結している。正面の失敗経路に合わせる |
| OCR PCHIP（全体 z） | **現行どおり残す** | 帯重なりの z は局所ロック。絶対 OCR には載せ替えない |
| pitch θ トレンドワープ | **残す（役割分担）** | 帯重なりは Run 内の局所 (z, pitch)。トレンドは低周波の θ。接合 1/2 ワープは方位間。二重に効き過ぎたらトレンドを弱める（オフは接合のあとで判断） |

### 3.1 縦割合（マッチ / 展開）

画像高さ H、主点 cy、焦点 fy。縦は光軸からの半高 `H/2` を 1.0 とする。

| キー（案） | 意味 | 使い方 |
| --- | --- | --- |
| `feature_matching_sideview.v_half_ratio` | マッチに使う縦。`|v−cy| ≤ ratio·(H/2)` | 光軸まわり（±Z）。横は 0..W−1（全幅） |
| `projection.v_forward_half_ratio` | 展開に使う進行方向の縦。`cy` から +Z へ `ratio·(H/2)` | −Z 側は塗らない。横は全幅 |

マッチは条件の良い近傍、展開は重なりと飛び埋めのためそれ以上に広くてよい。展開 ≥ マッチを推奨するが、コードは大小を強制しない（警告のみ）。

現行 `center_rect_half_ratio`（正方形）は廃止し、上記の縦帯＋全幅に置き換える。`usable_outer_radius_ratio` による円形マスクはピンホールでは使わない（矩形フレーム全体が有効）。

帯の Z 範囲は `max_dz × alpha` をやめる。展開縦帯の画素をピンホール逆投影した Z の min/max（進行方向、カメラ前方）を 1 フレームの帯幅とする。`motion.max_dz` は推定の上限のまま、描画幅とは独立。

### 3.2 帯重なり（側視）

同一 Run の既描画（画像1）と現帯（画像2）から ORB。leftover は帯 − 既描画。

| leftover | 意味 | 適用 |
| --- | --- | --- |
| `drow > 0`（η 下向きが +） | 帯が +η | `pitch = pitch0 − d_pitch` |
| `dcol > 0` | 帯が +z | `z = z0 − dz` |

符号は U（0°）の実測で固定し、他方向は同じ leftover モデルを使う。通ればその姿勢で取り直してから 1 回だけ書く。点数・RMS・η ビン悪化・上限 px のゲートは正面と同型を側視用に置く（キーは `two_direction.strip_overlap_*`）。

薄い帯が課題だった理由は、描画幅が `max_dz×α` だったことと、魚眼校正の折り畳みである。縦割合で展開を広げれば重なりは十分取れる想定。ゲートは側視用の点数下限を別値にしてよい。

### 3.3 失敗経路

`status==OK` の推定 dz が、OCR 窓平均（下限 mm 以上）の r 倍未満なら FAILED 相当。塗らず、`prev` は現フレームへ更新、z は履歴中央値（maxlen=10）で進める。通常の特徴点失敗も同じ z/prev 更新。統計は「特徴点抽出失敗」と「Z方向矛盾」を分ける。

連続失敗が展開帯幅を超えると穴は残る。帯を縦割合で広げても、失敗が帯幅以上続けば埋まらない（失敗回数の問題）。

## 4. 8 方向で壊れる現行の固定点

次は 3 方向前提なので、工程の前半で一般化する。

| 箇所 | 現行 | 8 方向 |
| --- | --- | --- |
| `TwoDirectionConfig.run_A/B/C` | 3 スロット | `runs: List[RunConfig]`（可変。n=2..8） |
| `product_runtime.resolve_named_run_videos` | `_U/_R/_L` → A/B/C | `_000`… と U/R/L 別名 |
| `SUFFIX_TO_PHYSICAL_ROLL_DEG` 等 | 3 値 | 45° 格子。任意 roll は 45° に量子化せず、設定値を正とする |
| `_CAPTURE_TO_PROGRAM_RPY_DEG` | 3 点表 | 拘束からの変換関数 |
| `SECTOR_CAMERA_CAR_DEG` / `OVERLAP_CENTER_*` / `SEAM_PAIRS` | U/R/L、120°、3 接合 | n と FOV から生成。接合は隣接のみ（周期 8） |
| `sector_blend_weight` の `/ 120.0` | ハードコード | 担当角 `360/n` |
| `mode_a_estimate_yaw_pitch` / `mode_a_use_frame_xy_residual` | U/R/L 分岐 | 光軸近傍判定。dz_only なら推定角は常に積まない |
| `SideviewProjectionMapper.calculate_dynamic_z_range` | `[z_cam, z_cam+max_dz·α]` | 展開縦割合 → Z |
| 円形 `usable_outer_radius_ratio` | 魚眼ディスク | ピンホールでは無効 |
| 仮想生成 `generate_two_direction_test_videos` | 魚眼 181°、U/R/L | ピンホール 60°、8 run |
| 接合の η=0 ラップ | R/L の 180° 線 | キャンバス切断 `θ=0`（car 180°）を含む担当帯が 1 本に載る。その Run の蓄積と接合 ORB は **θ 周期**必須 |

最終展開の周期切断は現行どおり **θ=0（真下側の η ラップ）** でよい。8 方向では 180° カメラの 45° 担当がこのラップを跨ぐ。3 方向で R/L 接合が跨いでいた問題が、1 カメラの帯の中に移る。`BestViewAccumulator` と接合 `remap` の周期パッドを、特定の run_id ではなく「担当帯が η=0 を含むか」で有効化する。

## 5. 工程

### 工程 0 — 本設計（完了、実装なし）

### 工程 1 — 方向の一般化（幾何・設定・入力）

依存: なし。

- `runs` リストと `n_directions` / `fov_deg` / `optical_axis_spacing_deg` を `two_direction` に追加。`run_A/B/C` は読み取り時に `runs` へ展開する互換だけ残す

### 工程 2 — ピンホール投影と縦割合

依存: 工程 1。

- 側視の `CoordinateTransformer` を pinhole（`r=f tan θ`）に切替。Kannala / `distort_ideal_pixels` は通さない
- マッチ ROI: 縦 `v_half_ratio`、横全幅。正方形 `center_rect` を削除
- 展開: `v_forward_half_ratio` から Z 範囲。`max_dz×α` と円形 outer mask を側視描画から外す
- `allow_signed_relative_z` は展開では使わない（進行方向のみ）。順投影テスト用に残してよい
- 単体: 主点画素は最近壁、+Z 帯幅が `R tan β` に一致、反対壁（η+180°）がマスクに入らないこと

### 工程 3 — 仮想ピンホール 8 方向動画

依存: 工程 2（生成と解析のレンズを一致させる）。

- `generate_two_direction_test_videos` に pinhole 60°、runs=8 を追加。校正 JSON オプションはピンホール経路では拒否
- metadata に `camera_model=pinhole`, `fov_deg=60`, `n_directions=8`, 各 run の physical_roll。`lens_calibration_file` は書かない
- 既知 z の `apply_generation_metadata_to_config` が校正パスを側視へ戻さないことをテスト

### 工程 4 — 移動量（dz_only と失敗経路）

依存: 工程 2（マッチ ROI）。工程 3 があると通し確認が楽。

- Mode A の積む量は dz のみ。Δpitch/Δyaw は推定しても捨てる（設定 `physical_attitude_source` 相当を側視に置く。値は `dz_only` 固定でよい）
- うなずきは従来どおり dz に載る前提を維持
- OCR 比異常 → FAILED、prev 更新、履歴中央値 dz、統計「Z方向矛盾」
- 通常 FAILED も prev 更新＋中央値（現行の凍結をやめる）
- STATIC 分岐は追加しない
- 実写確認は `test01_hp250_U.mp4` / `test02_hp250_U.mp4`（0° のみ、OCR）。同名 R/L は使わない

### 工程 5 — 同一 Run 帯重なり (z, pitch)

依存: 工程 2（帯が縦割合で十分重なること）、工程 4（塗るフレームの z が推定＋失敗経路で進むこと）。

- 側視用モジュール（例: `src/validation/sideview_strip_overlap.py`）。正面 `front_strip_overlap.py` は import しない
- 測定オン / 補正オンを別に持つ
- 取り直し成功時だけ書く。失敗時は補正前帯を書くかスキップするかは正面に合わせ、補正前を残して測定だけログする選択肢を設定で残す
- 符号テスト: 既知 leftover を合成した帯で (z, pitch) が引かれること
- Phase2 deroll は追加しない
- 実写確認は工程 4 と同じ U 2 本。接合はまだしない

### 工程 6 — 異方向接合の n 周期化と通し

依存: 工程 1（SEAM 生成）、工程 5（各 Run 部分図）。

- 隣接 8 接合、半分ずつ、担当帯内 θ 線形ブレンド。相手無しは 0
- η=0 を含む Run / 接合は周期パッド
- `sector_blend_weight` を担当角 `360/n` に
- pitch トレンドは既定オンのまま通し、帯重なりと二重ならトレンド窓を広げるかオフにする（工程 6 の観察で決める。設計段階では残す）
- OCR PCHIP は現行位置（接合の前）
- 製品 CLI で 8 本 → `mode_A/` に最終図。Excel / progress は側視スキーマのまま列を run 数に拡張（正面列は触らない）

### 工程 7 — 回帰の張り替え

依存: 工程 6。

- 3 方向魚眼前提のテスト（セクター 120°、U/R/L 専用、`max_dz×α` 帯幅、center_rect）をピンホール 8 方向／縦割合に更新

## 7. 役割分担（周方向と z）

```text
フレーム間マッチ     dz のみ
帯重なり（同一 Run） 局所の絶対 z と pitch（プログラム Euler の周方向）
OCR PCHIP            行程全体の z 縮尺
pitch トレンド        1 Run の低周波 θ
接合 1/2 ワープ       隣接方位の (Δz, Δθ)
deroll               しない
```

帯重なりで pitch を積んだあとトレンドが同じ方向を再度動かす場合は、トレンドを弱める。接合を正しいとする。

## 8. 確認項目（実装後）

- 反対壁（光軸+180°）が展開マスクに乗らない（ピンホール 60° では画角外）
- 展開帯の Z 幅が `R tan β` と一致し、`max_dz×α` に依存しない
- マッチは全幅×縦帯、展開は全幅×進行方向縦帯
- 隣接 15° が両 Run に塗られ、カット 22.5°+45k で担当が切り替わる
- η=0 を跨ぐ 180° カメラに黒帯（非周期 remap）が出ない
- 1 フレーム失敗（Z 矛盾）のあと、隣フレームの展開帯で穴が埋まること（連続失敗は除く）
- 帯重なりの leftover 符号が U と 90° で一致すること
- 正面テストが落ちないこと
